# AGENTS – Adjagent kb_tools

## kb build process decision-making guidance (`kb_survey`, `kb_docgraph`, `kb_claimgraph`, `kb_driver`)
- Best odds where certainty isn't available; never provably wrong where it is. No stage of this pipeline is certain, and the mechanical ones repeating an answer exactly is not the same as its being right. It reads documents written by people to no fixed standard, and every stage is a judgment with a failure rate. A mechanical rule that is usually right therefore earns its place — the alternative to a rule that sometimes misfires is not a correct rule, it is no rule and no result. What is never acceptable is being provably wrong inside a mechanical constraint: a check that can be evaluated and comes out false, a byte the contract says survives and doesn't, an invariant the code can test. That line is the whole distinction, and it is not a spectrum — certainty is mandatory exactly where it is available, and best odds are correct everywhere else. A constraint narrows in the specification first and never in answer to a red build: a state nothing evaluates is not a state nothing was wrong in.
- Weigh a result against what actually replaces it, which is usually nothing. Declining to record a relationship because some fraction of them will be wrong does not leave the graph cautious, it leaves it asserting the claim rests on nothing — a different wrong answer, arrived at silently, and one no later pass is prompted to revisit. This is structure — an edge, a node, a placement. A score is the other case: `*pending*` says *unscored* to every consumer, so nothing is silent, and a number nobody derived is a fabricated one rather than best odds.
- Inference is downstream of the odds, not a reason to raise the bar ahead of it. A mechanically-derived result is what the inference pass is handed to work from, and judging a candidate is cheaper and more accurate than composing one from nothing. A candidate the mechanical stage withheld is not a question the later pass answers badly — it is a question nobody asks it.
- **What inference is for is settled in `THESIS.md`, not here.** Read it before adding an inference step or widening one, and argue the step's scope against it in the report that lands the step.
- **Name the producer before you write the refusal.** Before writing code that refuses, raises, or reports a finding on a state, name what produces that state. Nothing on any reachable path produces it: the code is a second expression of a design the rest of the code already states, and deleting it costs nothing. The detector can also fire on something else — a token guard firing on a corpus that spells the token in prose: its only reachable outcome is a build failing for a reason that does not exist, which is worse than its absence. Making a failure survivable is a different act and this does not reach it.
- **A check earns its place by what it reads, not by where it sits.** It reads what arrived from somewhere this code did not compute — pandoc, a hand edit on the maintenance path, an operator reaching a runner target, a model's answer to one of our asks, a corpus authored to no standard. A check over a value this toolchain computed restates the computation. That list is where the boundaries have been, not a closed set; a new one is argued against the same test. Process separation is not that test: pass 1 and pass 2 are separate invocations, and what settles the checks between them is what `kb_write` can and cannot change, never that a new process started. **Each check argues its own case, in the report that lands it** — one check resembling another that earned its place is not an argument, and a comment asserting boundary status is the form that goes unaudited for the life of the code.
